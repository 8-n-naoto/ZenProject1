## 3. 承認フローの対象操作

1. イベントの確定（受付中 → 確定済）
2. 精算の確定（精算中 → 完了）
3. 完了イベントの再オープン（最高責任者のみ申請可）
4. 確定以降のサークル・商品・価格・共同購入リストの変更（「解禁」を申請し、変更後に再ロック）

可決条件: 対象グループの「責任者＋最高責任者」の過半数の賛成。最高責任者が承認した時点で即時可決。
申請者自身の1票は自動で賛成として計上する。否決も同様に過半数で確定する。

## 4. 精算アルゴリズム

1. 購入結果から**受益者 → 立替者**の債務を1件ずつ組み立てる
   - 受益者と数量は、購入希望から不足分（`purchase_result_shortage_users`）を引き、超過引取分（`excess_takeovers`）を足して決める
   - 金額 = `purchase_results.unit_price`（未入力なら `event_products.price`）× 数量
2. ユーザーごとの純額（受け取るべき額 − 支払うべき額）を求める
3. 純額がぴったり一致する組を先に相殺し、残りを金額の大きい順に突き合わせて **送金回数を最小化した送金リスト** を `settlements` に生成する
   （厳密な最小回数の決定は分割問題に帰着するため、実装は上記のヒューリスティック）
4. 金額は円単位の整数のみで扱い、割り算による端数は発生させない
5. 支払い報告（`payments`, status=reported）→ 受取確認（status=confirmed, `confirmed_by`）で `settlements` を完了にする
6. 全ての `settlements` が完了し、最高責任者の申請が可決されたイベントを「完了」とする
7. 支払い明細（`payment_items`）は、その支払い者の債務を金額の大きい順に切り出して作る。
   相殺により支払先が変わることがあるため、明細の相手と実際の立替者は一致しないことがある

### 精算の整合性について
- 精算中に購入結果を訂正すると、精算リストは自動的に作り直される（未精算のもののみ）
- 1件でも受取確認が完了した後は、購入結果の訂正も精算リストの再生成もできない（金銭が動いた後の遡及変更を防ぐため）

## 11. 承認フロー・金額の不整合への対応（2026-08-23）

| # | 論点 | 決定 |
|---|---|---|
| 40 | 立替者の保護 | 購入結果の立替者（返金の受取先）は、実際に購入した担当者から変えない。責任者が代理で訂正しても引き継ぐ |
| 41 | 金額の凍結 | 受取確認まで済んだ精算があるイベントでは、状態に関わらず購入結果を訂正できない。「精算中 → 開催中」への差し戻しも禁止（「完了 → 精算中」の再オープンは可） |
| 42 | 状態遷移の原子性 | 「精算中」への遷移は精算リストの生成と同一トランザクションで行う。失敗したら状態も戻す |
| 43 | 承認の膠着回避 | 最高責任者の反対は即時否決。申請者と最高責任者は承認待ちの申請を取り下げられる |
| 44 | 票の有効性 | 脱退・降格した人の票は数えない。責任者が増減したら承認待ちの申請を判定し直す |
| 45 | メールアドレスの変更 | 変更には現在のパスワードを求め、旧アドレス宛の再設定リンクは無効にする |
| 46 | 退会後の表示 | 退会した人の名前は「〜（退会済み）」として過去の記録に残す。関連画面はエラーにしない |
| 47 | 一括登録の入力 | 全角カンマ「，」も区切りとして扱う。マイナス価格・長すぎる商品名はエラーにする |
| 48 | リマインド | 同じ日に同じ人へ同じリマインドを2回送らない |
| 49 | パスワード再設定 | 送信・再設定の両方に回数制限（6回/分）を設ける |
| 50 | 役割の最低人数 | 昇格・降格・脱退・除名のいずれでも、責任者・最高責任者が0人になる変更は認めない |
| 51 | 検索 | キーワードは100文字までに丸め、LIKEのワイルドカード（% _ \）はエスケープする。ユーザー検索は2文字以上（総当たりでの列挙を防ぐ） |

| 60 | テストユーザーの作成 | `php artisan users:create-test` で、メール認証済み＝すぐログインできるユーザーを作れる。ログインID省略時は `test001` から順に採番し、**退会済みユーザーのIDは使い回さない**。`--count` でまとめて作成、`--group` `--role` で既存グループに参加、`--unverified` で未認証、`--force` で既存IDのパスワード再設定（退会済みなら復帰）ができる |
| 61 | 本番での実行 | 上記コマンドはパスワードが分かりきったアカウントを作れるため、**本番環境では実行を拒否する**（`--force` でも通さない） |
| 62 | 入力ルールの一元化 | ログインID・表示名・メールアドレス・パスワードの検証ルールは `App\Support\AccountRules` に集約し、会員登録・プロフィール編集・上記コマンドがすべてここを参照する。片方だけルールが変わって食い違うことを防ぐ |
| 63 | デモデータとの使い分け | グループ・イベント・精算まで含む一式は `DemoSeeder`、任意IDの単発作成は `users:create-test` と役割を分ける |
